# 数据中心冷通道空间复核

轻量级复核工具 —— 让传感器记录里的异常对象**不再藏着掖着**，支持原始数据保留、备注双向同步、待确认流程、Markdown 报告一键导出。

## 三步上手

```bash
# 1. 安装依赖
npm install

# 2. 启动（前端 + 后端同时跑）
npm run dev
#   → 前端 Vite   : http://localhost:5173（若端口占用会自动升到 5174/5175/5176…）
#   → 后端 Express : http://localhost:3001

# 3. 浏览器打开 http://localhost:5173
#    页面中央会看到「工具尚未初始化」空态卡片，
#    → 点「初始化并加载数据」（会调用 POST /api/records/seed 生成 mock 数据）
#    → 随后到「复核总览」点「执行相邻点位检测」即可看到待确认事项。
```

## 核心能力速览

| 你想做什么 | 去哪里 |
| --- | --- |
| 一眼看有多少异常 / 待确认 / 脏数据 | 「复核总览」顶部 4 个统计卡 |
| 揪出相邻点位合错 / 温差异常 / 编号缺口 | 「复核总览」→ 「执行相邻点位检测」 |
| 看一条异常的空间位置、影响范围、改备注、改状态 | 点「待确认清单」任意一项，进入「异常详情」 |
| 确认传感器原始数据到底有多脏（不做清洗） | 「传感器记录」页，行底色标红 = 脏数据；`raw_values` 原样保留 |
| 按状态 / 点位筛选导出 Markdown 报告 | 「报告导出」页，实时预览 + 下载 `.md` |
| 就想单独导出一个异常对象给同事 | 「报告导出」左侧「单独导出一个异常对象」列表 |

## 🚨 坏材料来了看哪里

（当拿到一批**不齐整、点位合错、缺字段**的传感器数据时，按此顺序排查）

### 1. 先看原始数据有没有被偷偷改过？ → `api/data/sensor_records.json`

**我们的原则：脏数据绝不动。**

每条记录都带一个 `raw_source` 字段：

```jsonc
{
  "point_id": "A-01-05",
  "temperature": null,         // 程序读到的 null
  "is_dirty": true,             // 脏数据标记
  "dirty_reason": "温度字段缺失（原始值为 N/A）",
  "raw_source": {
    "file_name": "dc_sensors_2026Q2.csv",   // ← 原始文件名
    "import_time": "2026-06-10T08:00:00Z",  // ← 导入时间
    "line_number": 7,                       // ← 原始行号
    "raw_values": {                          // ← 所有原始字段的逐字抄录
      "温度(℃)": "N/A",
      "湿度(%)": "45",
      "...": "..."
    }
  }
}
```

- **前端页面：「传感器记录」** 列头有专门的「原始来源」两列，最后一列 `raw_values` 节选可展开看全。
- 脏数据行**左侧玫瑰红竖条 + 底色浅红**，鼠标悬浮可看原始文本。

### 2. 相邻点位合错了，会不会程序自己悄悄算完？ → 不会，先去「待确认清单」

工具检测到以下**任意一种**情况，**绝不会自动下结论**，统一挂「待确认」：

| 检测类型 | 触发条件 | 给你的原因说明里会有 |
| --- | --- | --- |
| 数值缺失 `missing_value` | 温度 / 湿度读不到或不是数字 | 缺失哪个字段、原始值是啥 |
| 编号缺口 `gap` | 同一行列号不连续（如 03 → 06） | 缺了哪些列号 |
| 温差过大 `temp_delta` | 相邻两点温度差 > 5℃ | 具体差值、对比点、阈值 |
| 重复编号 `duplicate` | 同一点位 ≥2 条记录 | 重复次数、分别来自哪个文件 |

待确认项在**复核总览左侧清单**，点进去：
- 上方平面图会用**虚线/橙色**圈出「影响范围」点位
- 右侧是完整 `raw_source` 和 `raw_values`
- 评审助理可以「确认异常」或「驳回（误报）」，每一步都写进 `operation_logs`

### 3. 运营主管改了备注，导出时对不上怎么办？ → 不会对不上

**备注修改的链路：**

```
前端「异常详情」textarea 输入
    └─► 防抖 500ms 后 PATCH /api/anomalies/:id/remark
           └─► FileStorage 原子写入 anomalies.json（先 .tmp，再 rename）
                  └─► 下次生成报告 /api/report 时实时从 anomalies.json 读
```

想自己验证：
1. 在「异常详情」里随便改一句备注（比如"现场已确认为传感器漂移"），等右侧出现 **「✓ 已同步到导出」**。
2. 去「报告导出」→ 「刷新预览」，搜那句话，一定能搜到。
3. 或者直接点页面上的 **「下载 .md」**，打开看。

### 4. 重启 / 重跑会不会丢状态 / 丢备注？ → 不会

- **传感器原始数据**持久化在：`api/data/sensor_records.json`
- **异常对象 + 状态 + 备注 + 操作日志**持久化在：`api/data/anomalies.json`
- **历史导出的 Markdown 报告**持久化在：`api/data/reports/`

三批文件启动时自动从磁盘读回，不需要数据库。

> 💡 **交接小贴士**：把整个 `api/data/` 目录打包给接手人就能 100% 还原现场。
> 程序只做 `fs.writeFile(tmp) + fs.rename` 原子写入，断电不会写坏半条 JSON；
> 如果真的写坏了，删掉同名 `.tmp` 残留文件即可。

按操作顺序：

| # | 检查点 | 预期 | 若不对看哪里 |
| --- | --- | --- | --- |
| 1 | 启动 `npm run dev` 后，终端里两条日志都出现 | Vite `ready in xxx ms` + Express `Server on :3001` | 若 3001 被占用：`lsof -i:3001` 查进程 |
| 2 | 浏览器打开后**页面顶部不出现红色错误条** | 白色 header + 深蓝侧栏 + 中央「尚未初始化」卡片 | 出现红条：大概率后端 3001 没起，或 seed 路由错配（见风险 §2） |
| 3 | 点「初始化并加载数据」按钮 | 按钮变禁用 + Play 图标 spin + 1~2s 后 4 张统计卡有数字（56 / 4 / 4 / 0） | 卡超过 10s：看浏览器 Network，`POST /api/records/seed` 是否 200 |
| 4 | 「复核总览」→「执行相邻点位检测」 | 按钮变禁用，pending 数从 4 涨到 6~10；左侧待确认清单出现新项 | 没涨：Network 里 `POST /api/detect/adjacent` 返回 |
| 5 | **确认检测不跨区**：找到 A-01-08 的温差项，点进去看「影响范围」 | 只含 A 区点位（A-01-07 / A-01-08 / A-01-09 等），**绝不含 B 区点位** | 出现 B-01-xx 之类：`DetectionService.groupByZoneRow` 分组逻辑有问题（见 `api/services/DetectionService.ts`） |
| 6 | 任意待确认项 → 进「异常详情」→ **改备注** | 输入后下方先显示「保存中…」，1s 内变绿字「✓ 已同步到导出」 | 一直红：看 `PATCH /api/anomalies/:id/remark` 的 body |
| 7 | 去「报告导出」→ 搜你刚写的备注字 | 实时预览区 Markdown 里**能搜到那句话** | 搜不到：点一下「刷新预览」再试；或检查 `POST /api/report` 返回 |
| 8 | 关闭终端 → 重新 `npm run dev` → 回同一路由 | 刚才改的备注、异常状态**还在** | 丢了：检查 `api/data/anomalies.json` 是否真的写入了 |
| 9 | 「传感器记录」→ 打开「仅脏数据」筛选 | 表格里只剩 2~3 行带玫瑰红底色的脏数据；筛选无结果时显示友好空态卡 | 一片空白：看 §SensorRecords 修复，确认 rows.length===0 分支是否命中 |
| 10 | 「报告导出」→ 点位范围**只填起始**不填结束 | 输入框下方出现**黄色告警**「当前范围筛选未生效」 | 没告警：ReportExport §halfFilledRange 变量 |

## ⚠️ 剩余风险（接手人提前知道，不算 Bug）

1. **重复异常冗余**  
   `SeedService` 首次 seed 已预埋 anm_001~004（4 条），再点「执行相邻点位检测」会用 `DetectionService` 重新算一遍，对于同点位同类型的异常，会生成 id 不同的第二条 `pending`。  
   - **影响**：待确认清单里会出现两条描述几乎一样的异常（如 A-01-05 的温度缺失会出现 2 条）。  
   - **不阻塞**：数据语义没问题，只是冗余，用户可自行把其中一条「驳回」。  
   - **未来可优化**：`AnomalyService.addMany` 里按 `point_id + detection_reason.type + status=pending` 做去重。

2. **点位范围是字典序比较**  
   报告导出里的 `point_range` 过滤目前用的是 `String.localeCompare`。对于 `A-01-10` 与 `A-01-2`，字典序里 `"10" < "2"`（因为第一位 `1 < 2`）。  
   - **影响**：若起止填 `A-01-01` ~ `A-01-10`，会漏掉 `A-01-02` ~ `A-01-09`。  
   - **规避**：填时按真实使用习惯选完整区段（如 `A-01` 区直接用状态筛选，不依赖 range）。  
   - **未来可优化**：ReportService 里把 `point_id` 按 `-` 切段后**逐段整数比较**。

3. **单机并发写 JSON 可能冲突（理论上）**  
   `FileStorage` 的原子写入是 **`writeFile(tmp) + rename`**，能防半写损坏，但如果同时开两个浏览器页改同一条异常的状态，后面的会覆盖前面的。  
   - **实际无影响**：这是「交接友好的小工具」，单人单机用，不存在多人并发。  
   - **如要扩展**：加基于文件的简单锁（`fcntl` 或 `.lock` 文件）。

4. **数据目录未创建时的首次启动**  
   `api/data/` 目录若不存在，`FileStorage` 里 `mkdirSync(path, { recursive: true })` 会在第一次写时自动创建；但 `listReports` 在目录不存在时返回 `[]`，不会报错。  
   - **现状 OK**，接手人直接 `npm install → npm run dev` 不会踩坑。
