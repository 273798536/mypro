# 外协加工对账权限追责台账系统

## 系统概述

本系统针对外协加工对账中的核心痛点：**同一批半成品分批返工后结算单容易多扣**、**出现问题就牵出一堆材料难追溯**，提供了完整的批次级对账台账解决方案。

### 核心特性

1. **按批次完整保留证据链**：外协送货单 → 返修记录 → 扣款明细 → 短信截图证据 → 门店交接纸
2. **完整的状态流转机**：草稿 → 提交 → 驳回 → 二次确认 → 只读审计
3. **每步操作留痕**：所有状态变更前后快照对比，支持差异回显
4. **批次重复处理策略**：同一批数据跑两次，可选择「忽略 / 覆盖 / 追加」
5. **异步任务分级失败**：等重试 / 等人工 / 永久失败，服务重启后自动恢复
6. **角色视图差异化展示**：工厂老板看全貌，审计看脱敏数据
7. **异常项报表可见**：待复核、无法处理项不只是日志，导出时明确去向

## 核心业务流程

### 标准流程：正常对账

```
操作员建账(草稿)
    ↓
提交(记录快照before)
    ↓
财务确认(记录快照after)
    ↓
标记为"正常"结果
```

**操作步骤**：
1. 操作员 POST `/api/ledgers` 创建台账
2. POST `/api/ledgers/:id/submit` 提交
3. 财务 POST `/api/ledgers/:id/confirm` 确认
4. POST `/api/ledgers/:id/result` 设置结果 `normal`

### 异常流程1：待复核

```
同一批次两次返工 → 系统标记待复核
    ↓
财务主管人工介入
    ↓
确认通过 or 驳回修改
```

**触发场景**：同一批次返工记录 ≥ 2 条

**修正方式**：
- 人工核查返修原因真实性
- 确认后正常确认
- 或驳回要求操作员补充证据

### 异常流程2：无法处理

```
送货单无签字 / 供应商不认 / 证据缺失
    ↓
标记为"无法处理"
    ↓
导出报表时进入异常项分析表
    ↓
建议：找原始物流凭证 / 协商解决
```

## 批次重复处理策略

当同一 `batchNo` 的数据重复提交时：

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| `ignore` | 跳过不处理，返回原有台账 | 每日定时同步，避免重复建账 |
| `overwrite` | 删除原数据，完全重写 | 对账数据全盘修正 |
| `append` | 在原有基础上追加记录 | 同一批次分次送货 / 分次返工 |

**API 调用**：
```bash
POST /api/ledgers/batch
{
  "data": { ...台账数据... },
  "strategy": "overwrite"  # ignore | overwrite | append
}
```

## 异步任务失败处理

### 任务状态流转

```
PENDING → PROCESSING → COMPLETED
                ↓
            失败
                ↓
    ┌───────────┴───────────┐
    ↓                       ↓
重试次数<3              重试次数≥3
    ↓                       ↓
WAITING_RETRY        PERMANENT_FAILED
(定时自动重试)        (需人工介入)
```

### 失败分级说明

| 状态 | 含义 | 处理方式 |
|------|------|---------|
| `waiting_retry` | 等待重试 | 系统每5分钟自动重试，无需人工干预 |
| `waiting_manual` | 等待人工 | 需要运营人员核查后操作 |
| `permanent_failed` | 永久失败 | 重试3次仍失败，彻底放弃 |

### 恢复机制

服务重启后，调度器会自动扫描：
- 所有 `pending` 状态任务
- 所有 `waiting_retry` 且到时间的任务

**不会丢任务，服务恢复后接着跑**。

## 变更历史与快照

### 变更历史

每条变更记录包含：
- 字段名 (fieldName)
- 原值 → 新值
- 操作人 + 角色
- 变更原因
- 变更时间

**API**：`GET /api/ledgers/:id/history`

### 前后快照对比

每次核心操作（提交、驳回、确认、覆盖等）都会自动保存两份快照：
- `before`: 操作前的完整数据
- `after`: 操作后的完整数据

**API**：`GET /api/ledgers/:id/diff/submit`

## 导出功能

### 单笔台账导出

```bash
GET /api/ledgers/:id/export?maskSensitive=true&includeHistory=true
```

导出内容（多Sheet Excel）：
1. **台账概览**：批次、状态、处理结果、各表数量统计
2. **外协送货单**：明细列表
3. **返修记录**：明细列表
4. **扣款明细**：明细列表
5. **门店交接纸**：明细列表
6. **短信证据**：明细列表
7. **变更历史**（可选）：所有变更记录

### 汇总报表导出

```bash
GET /api/ledgers/export/report?includeFailures=true
```

包含：
- 所有台账汇总行（批次、状态、处理结果、扣款金额等）
- **异常项分析表**（当 `includeFailures=true` 时）：
  - 待复核项 + 处理建议
  - 无法处理项 + 问题说明
  - 已驳回项 + 驳回原因

## 样例数据说明

运行 `npm run seed` 后会创建 3 笔典型台账：

### 1. BATCH-2024-001 - 正常结果

**场景**：标准的送货 → 少量返工 → 扣款 → 确认流程

- 5000个不锈钢外壳
- 200个表面划痕返工（抛光处理）
- 扣款 500 元
- 已附供应商确认短信截图证据
- **处理结果：normal**

### 2. BATCH-2024-002 - 待复核

**场景**：同一批次出现两次返工，触发复核预警

- 10000片PCB主板
- 第一次：1500片焊点不良补焊
- 第二次：800片元件贴装偏移重贴
- 扣款合计 4500 元
- **处理结果：pending_review**
- 说明：同一批次两次返工，需财务主管复核

### 3. BATCH-2024-003 - 无法处理

**场景**：证据链缺失，系统无法自动判定

- 20000个塑料按键
- 送货单无对方签字
- 实际收货少 2000 个
- 供应商不认，双方僵持
- **处理结果：unprocessable**
- 说明：需找原始物流凭证或协商解决

## 失败路径与修正方式

### 常见失败场景

| 失败场景 | 状态 | 修正方式 |
|----------|------|---------|
| 网络波动导致扣款计算失败 | waiting_retry | 系统自动重试 |
| 供应商API超时 | waiting_retry | 系统自动重试 |
| 数据格式解析错误 | permanent_failed | 修复数据格式后重新提交 |
| 对账不平，差额过大 | waiting_manual | 财务人工介入调账 |
| 证据不足无法判定 | unprocessable | 补充原始凭证后重新走流程 |

### 报表变化说明

当处理结果变更时，汇总报表会相应变化：

| 处理结果 | 报表位置 | 颜色标记 |
|----------|---------|---------|
| normal | 主表正常行 | 无 |
| pending_review | 主表 + 异常分析表 | 黄色 |
| unprocessable | 主表 + 异常分析表 | 红色 |
| rejected | 主表 + 异常分析表 | 灰色 |

## 给工厂老板的看重点

1. **角色视图清晰**：你看到的是完整数据，审计看到的是脱敏后的数据
2. **变更原因可追溯**：每笔扣款、每次驳回都有明确原因和操作人
3. **异常项不埋没**：待复核、无法处理的项在报表最前面，不是混在日志里
4. **不是一堆汇总数**：点击任何数字都能追溯到原始送货单、返修单、短信证据
5. **失败有去处**：异步任务不会悄无声息失败，每级失败都有对应处理流程
