# 长租公寓押金退还服务 - 启动说明

## 项目架构

```
押金账本(DepositLedger)
    ├── 租约合同(LeaseContract) 1:N
    ├── 押金流水(DepositFlow) 1:N
    ├── 水电账单(UtilityBill) 1:N
    ├── 维修工单(RepairOrder) 1:N
    ├── 账本明细(DepositLedgerItem) 1:N
    ├── 审计日志(AuditLog) 1:N
    └── 争议处理(Dispute) 1:N
```

## 核心设计原则

1. **统一计算入口**：所有押金计算走同一套 `calculate_deposit_ledger` 函数，避免各接口各算各的
2. **抵扣顺序统一**：未缴水电费 → 免租期误扣调整 → 租客责任维修 → 其他扣款
3. **状态来源统一**：争议状态、待确认分支全部从账本明细自动推导
4. **改动全追踪**：所有更新都走审计日志，补录维修责任后能看到哪些结论被改动
5. **持久化**：SQLite数据库，重启后数据不丢失

## 核心接口说明

### 押金账本计算
```
POST /deposit-ledgers/calculate
```
统一入口，传入合同ID和账本编号，自动：
- 汇总未缴水电费
- 检测免租期误扣
- 计算租客责任维修
- 识别待核责的维修工单
- 生成争议记录并指派核责人
- 记录审计日志

### 双向追溯

**正向查询（租约→结果）**：
```
GET /trace/forward/{contract_no}
```
从租约合同号查到最终押金账本、关联的流水、账单、维修工单。

**反向查询（结果→流水）**：
```
GET /trace/backward/{ledger_id}
```
从账本ID反查关联的押金流水，展示每条扣款的来源。

### 补录核责

**确认维修责任**：
```
POST /repair-orders/{order_id}/confirm-responsibility
```
补录后重新调用计算接口，审计日志会记录哪些结论被改动。

### 争议处理

```
GET    /disputes/                    待核责列表
PATCH  /disputes/{dispute_id}        处理争议，填写解决意见
```

**核责人自动指派规则**：
- 免租期误扣 → 运营主管
- 维修争议 → 维修主管
- 水电补录 → 财务主管
- 其他争议 → 店长

### 月底导出复盘

```
GET /export/monthly?year=2024&month=12          JSON格式
GET /export/monthly/download?year=2024&month=12  CSV格式
```

导出字段：账本编号、合同编号、租客姓名、房间号、押金总额、扣款总额、应退金额、状态、是否有争议、争议数量、计算时间、确认时间。

## 典型业务流程

### 场景1：正常退租（无争议）
1. 创建租约合同 → 录入押金流水 → 退租结算
2. 调用 `/deposit-ledgers/calculate` 计算
3. 状态为 `calculated` → 确认后状态改为 `confirmed`
4. 月底导出

### 场景2：免租期误扣
1. 计算时检测到押金流水与合同约定不符
2. 状态自动设为 `pending_rent_free_confirm`
3. 争议记录指派给运营主管
4. 运营主管确认后，修改争议状态为 `resolved`
5. 重新计算账本，确认退款

### 场景3：维修责任待确认
1. 计算时发现维修工单责任未明确
2. 状态自动设为 `pending_repair_confirm`
3. 争议记录指派给维修主管
4. 调用 `/repair-orders/{id}/confirm-responsibility` 确认责任
5. 重新计算账本，审计日志记录改动

### 场景4：水电费未缴
1. 计算时发现未缴水电费账单
2. 状态自动设为 `pending_utility_confirm`
3. 争议记录指派给财务主管
4. 租客补缴后标记账单为已缴
5. 重新计算账本
