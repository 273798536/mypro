### 数据文件位置
```
data/field_samples.json
```

### 数据字段说明（JSON格式）
```json
{
  "sample_id": "SAMPLE-001",        // 样本编号，必填
  "vertices": [0, 1, 2, 3, 4],      // 顶点列表
  "edges": [[0,1], [1,2], ...],     // 边列表（无序对）
  "expected_cut_points": [2, 3],    // 预期的割点答案
  "source": "课堂作业_第3章_第12题", // 数据来源，必填
  "version": "1.0",                 // 版本号，必填
  "created_at": "2026-06-15T09:30:00",
  "updated_at": "2026-06-15T09:30:00",
  "is_duplicate": false,            // 是否为重复样本
  "duplicate_of": null,             // 重复的原样本ID
  "supplementary_note": null,       // 补录说明（非常重要！）
  "boundary_flag": false,           // 是否为边界样本
  "boundary_reason": null,          // 边界原因说明
  "metadata": { "description": "..." }
}
```

### ⚠️ 重要：为什么要有补录说明？
> "参数版本被同学改过却没有记录" —— 这是老叶最头疼的问题。

**`supplementary_note` 字段就是为了解决这个问题设计的。** 任何时候修改数据、讨论结论、学生提问，都应该记录在这里。比如：

```json
"supplementary_note": "2026-06-20复核发现：此样本与SAMPLE-001数据完全相同，但提交人不同。已与两位同学确认，系合作完成后分别提交，不属于抄袭。但为保证数据一致性，两条记录均保留，此标记用于触发人工复核流程。"
```

## 🎯 三类复核状态说明

### ✅ 安全（Safe）
**状态含义**：算法结果与预期一致，数据完整，无异常标记。

**典型场景**：
- 普通样本，结果匹配
- 数据校验通过
- 无边界标记、无重复、无补录说明

**操作建议**：在复核表上签字确认即可。

---

### ⚠️ 待确认（Pending）
**状态含义**：存在需要人工核对的疑点，但不致命。需要老叶或相关同学确认后再定。

**典型触发场景**：
1. **边界样本**：包含桥端点、孤立点、单点图等特殊情况
2. **重复样本**：检测到与其他样本数据完全一致
3. **有补录说明**：之前的讨论记录需要确认是否已解决
4. **版本变更**：创建时间≠更新时间，需要确认修改记录
5. **结果略有出入**：算法结果与预期差1-2个点

**复核时需要做的**：
- 查看"待确认事项"列表
- 逐一核对每个疑点
- 在备注栏写明结论：已确认 / 需修改 / 退回重算

---

### ❌ 需补材料（Missing）
**状态含义**：缺少必要材料或校验失败，必须补齐后才能进入复核。

**典型触发场景**：
1. **必填字段缺失**：样本ID、来源、版本号为空
2. **校验和不匹配**：数据可能被篡改或版本更新后未重新计算
3. **算法运行失败**：图数据格式错误
4. **结果严重不符**：算法结果与预期差≥3个点

**操作建议**：按"需补材料清单"补充完整，再重新提交复核。

## ❌ 常见失败场景

### 场景1：数据被篡改（校验和不匹配）
**现象**：同学修改了图的边但没更新版本号和校验和

**报错**：`数据校验和不匹配（记录：xxx，当前计算：yyy）`

**处理步骤**：
1. 与提交同学确认修改是否经过授权
2. 如属正常修改，请更新版本号（如 1.0 → 1.1）
3. 重新计算校验和并更新记录
4. 在 `supplementary_note` 中记录修改原因

---

### 场景2：重复样本（不同提交人，数据相同）
**现象**：两位同学合作完成后分别提交，数据完全一致

**报错**：`检测到此样本与 SAMPLE-001 数据完全一致（校验和相同）`

**处理步骤**：
1. 与两位同学确认是否为合作完成
2. 如属合作，保留两条记录并标记 `is_duplicate: true`
3. 在 `supplementary_note` 中说明情况
4. 复核状态设为"待确认"，人工确认后签字

---

### 场景3：边界样本判定存疑
**现象**：桥的端点是否应算作割点存在争议

**报错**：`此条为边界样本：顶点2是桥的端点，移除后图分裂为2个分量`

**处理步骤**：
1. 参考补录说明中的历史讨论
2. 按教材定义：割点 = 移除后连通分量增加
3. 桥的端点满足定义，应判定为割点
4. 在备注栏写明判定依据

---

### 场景4：缺少必要字段
**现象**：样本缺少来源或版本号信息

**报错**：`来源信息缺失或为默认值'unknown'`

**处理步骤**：
1. 退回提交人补充完整信息
2. 必填字段：`sample_id`, `source`, `version`, 图数据
3. 补充完整后重新提交复核

---

### 场景5：算法结果与预期不一致
**现象**：Tarjan算法结果与历史答案有出入

**报错**：`算法结果与预期不一致。预期有但没检测到：[2]`

**处理步骤**：
1. 先检查图数据是否录入错误
2. 再用手工演算验证预期答案
3. 如预期有误，更新 `expected_cut_points`
4. 如算法有误，检查Tarjan实现逻辑
5. 差异≥3个点时状态为"需补材料"，否则为"待确认"

## 📐 边界条件说明（人话版）

### 什么是割点？
> **人话解释**：一个图里，如果去掉某个点之后，原来连通的图裂成了好几个互不连通的部分，那这个点就是割点。就像一座桥的桥墩，拆了桥就断了。

> **数学定义**：G是连通图，v∈V(G)，若G-v不连通，则v是G的割点。

### 常见边界情况对照表

| 边界类型 | 判定说明 |
|---------|---------|
| **1. 桥的端点** | ✅ 是割点。桥=去掉后图分裂的边，它的两个端点自然也是割点。 |
| **2. 星型图中心** | ✅ 是割点。去掉中心后所有叶子都孤立。 |
| **3. 孤立点（度=0）** | ❌ 不是割点。本来就不连通，去掉后连通分量数没增加。 |
| **4. 单点图（只有1个点）** | ❌ 不是割点。去掉后分量从1变0，不满足"增加"。 |
| **5. 仅连接两个分量的点** | ⚠️ 边界割点。虽然是割点，但只连接两个分量，属于边界情况需特别注意。 |
| **6. 双连通分量中的点** | ❌ 不是割点。双连通=任意两点间有至少两条不相交路径，没有单点故障。 |

### 单位问题
- ⚠️ 图论里的"割点"没有物理单位，就是顶点的编号（整数）。
- ⚠️ 注意区分"顶点编号"和"顶点数量"，别搞混了。
- ⚠️ 边是无序对：`(u,v)` 和 `(v,u)` 是同一条边，录入时别重复。

### 复核时的关注点
1. **结果对不对？** 算法找的割点和预期一致吗？
2. **是不是边界情况？** 有没有桥端点、孤立点这些特殊情况？
3. **数据改没改？** 校验和匹配吗？版本号更新了吗？
4. **重复了吗？** 有没有其他样本和这条数据一模一样？
5. **有补录说明吗？** 之前的同学有没有留下什么注意事项？

## 💻 换台电脑也能跑

## 💡 设计理念

1. **不做漂亮壳子，只解决真问题**：没有花哨的界面，但该有的流程一个不少。
2. **数据留痕，防止扯皮**：校验和 + 版本号 + 补录说明，谁改了什么一目了然。
3. **边界情况提前预警**：不让老叶再花时间抠代码，常见边界直接标出来。
4. **重复样本不忽略**：专门设计了重复检测机制，确保走到复核分支。
5. **文案贴近日常交接**："安全/待确认/需补材料"，就像平时说话一样自然。
