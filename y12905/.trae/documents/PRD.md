# 提示词版本灰度看板 - 产品需求文档 (PRD)

## 1. 产品概览

### 1.1 产品定位
面向 MLOps 工程师的提示词（Prompt）版本灰度评测与管理平台。解决人工反馈迭代后，安全规则与评测结论的同步性问题，提供可追溯、可复核的全流程闭环。

### 1.2 核心用户
- **MLOps 工程师**：日常使用者，负责提示词版本管理、灰度对比、规则更新
- **业务方**：结果消费者，接收评测结论，区分可直接用 / 需复核的结果

### 1.3 设计原则
1. **跑稳优先**：灰度对比和分布统计必须稳定可靠
2. **可操作反馈**：错误必须指向具体解决路径，不抛内部错误
3. **一致性**：页面摘要与导出文件结论必须完全一致
4. **人工反馈闭环**：反馈修改必须联动提示安全规则是否需要变更

## 2. 核心功能需求

### 2.1 提示词版本管理
| 功能 | 描述 | 优先级 |
|------|------|--------|
| 版本列表 | 展示所有提示词版本（版本号、创建时间、变更描述、状态） | P0 |
| 版本详情 | 查看完整提示词内容、关联的安全规则版本 | P0 |
| 版本录入 | 通过 API 录入新提示词版本（含安全规则快照） | P0 |

### 2.2 灰度对比看板（P0 - 核心）
- 选择 A/B 两个提示词版本进行对比
- 逐样本展示两版输出差异（diff 高亮）
- 统计指标：通过率变化、安全违规次数、平均响应时长
- **关键联动**：对比结果标记"安全规则需复核" / "结论可直接使用"

### 2.3 分布统计视图（P0 - 核心）
- 评分分布直方图（1-5 分 / 或 PASS/FAIL 分布）
- 安全违规类型分布饼图
- 多版本叠加对比曲线
- 按时间维度的趋势变化

### 2.4 评测回放（P1）
- 选择历史评测任务，回溯结论来源材料
- 点击某条结论，跳转到对应样本的原始输入 + 模型输出 + 标注员反馈
- 支持"结论溯源"：结论 → 标注记录 → 原始样本

### 2.5 人工反馈与安全规则联动（P0）
- 反馈状态机：
  - 🟢 **可直接用**：评分 ≥ 阈值 & 无安全违规 & 规则未改动
  - 🟡 **待 MLOps 复核**：评分波动 > 阈值 / 安全规则版本变更
  - 🔴 **需重新评测**：提示词本体改动 > N 字符 / 新增安全规则
- 反馈修改后，自动计算：安全规则是否受影响？结论是否需要更新？

### 2.6 导出功能（P1）
- 格式：CSV / JSON
- 导出内容与界面摘要一致性校验（哈希比对）
- 导出时带版本快照，确保可回溯
- **禁止不一致**：界面显示"通过"的样本，文件中不能为"待确认"

### 2.7 错误处理（P1 - 体验关键）
- 缺版本错误：`"评测任务 #123 引用了提示词版本 v2.5，但数据库中未找到该版本。请先通过 POST /api/prompt-versions 录入 v2.5"`
- 缺样本错误：明确指出缺失的 sample_id 列表
- 规则冲突错误：指出具体哪条安全规则版本不匹配

## 3. 用户故事

### 故事 1：MLOps 工程师从空目录跑通全流程
> 作为 MLOps 工程师，我希望拿到一套 curl 示例，从空目录开始 5 分钟内跑通：建版本 → 提交评测 → 看对比 → 导出结果，这样我能快速验证方案。

**验收标准**：
- README 含完整步骤：依赖安装 → 启动 → 种子数据 → curl 示例
- 第一条样例数据位置明确标注
- 全部 curl 可直接复制运行

### 故事 2：人工反馈修改后判断规则是否要变
> 作为 MLOps 工程师，当我修改了某条标注反馈后，系统自动告诉我："这条反馈涉及 v1.2 安全规则 #R-007，建议同步复核规则"，而不是让我自己去翻历史。

**验收标准**：
- 修改反馈时，自动关联受影响的安全规则 ID
- 看板上明确标记"🔴 关联安全规则变更，需复核"

### 故事 3：业务方分清结果可用性
> 作为业务方，拿到评测报告时，我一眼就能看出哪些结论可以直接发给产品（🟢 可直接用），哪些必须找 MLOps 再确认（🟡 待复核）。

**验收标准**：
- 列表每行前置状态色块，颜色语义全局一致
- 导出文件同样包含 status 字段（APPROVED / REVIEW_REQUIRED）
- 界面摘要卡片的数字与导出文件统计完全一致

### 故事 4：出错时知道怎么修
> 作为使用者，当我提交评测失败时，错误信息告诉我缺哪份版本数据，而不是 Internal Server Error。

**验收标准**：
- 所有 API 错误码 ≥ 400 时，response.body 包含：error_code、message、action（修复建议）
- 不存在 Internal Server Error 直接暴露给用户

## 4. 非功能需求

| 维度 | 要求 |
|------|------|
| 本地运行 | SQLite 数据库，零配置，单命令启动 |
| 数据量 | 支持 10k 条评测样本流畅渲染 |
| 启动速度 | 后端 < 3s，前端热更新 < 2s |
| 可移植 | 全部依赖通过 requirements.txt / package.json 锁定版本 |
| 一致性 | 导出文件与界面摘要 MD5 校验一致 |

## 5. 数据模型（核心实体）

```
PromptVersion         提示词版本
├── id, version_tag, content, created_at
├── safety_rules_snapshot (JSON: 安全规则快照)
└── change_log

EvalSample            评测样本
├── id, prompt_version_id (FK)
├── input_text, model_output
├── score, safety_violations (JSON 数组)
├── eval_status: PASS/FAIL/REVIEW
└── source_material_ref (来源材料 ID)

GrayCompareTask       灰度对比任务
├── id, version_a_id, version_b_id
├── metrics_summary (JSON: 通过率、违规数、波动)
├── created_at, status
└── consistency_flag: 安全规则是否一致

HumanFeedback         人工反馈
├── id, eval_sample_id, evaluator, feedback_text
├── original_score, revised_score
├── affects_safety_rules: true/false
├── affected_rule_ids (JSON 数组)
└── final_decision: APPROVED / REVIEW_REQUIRED / RERUN
```

## 6. 界面设计方向

### 美学基调：工业级 MLOps 控制台
- **深色模式**为主（代码/数据密集场景，护眼），支持浅色切换
- **等宽字体**展示 diff 和代码片段
- **状态颜色**作为核心视觉锚点：
  - 🟢 绿 = 可直接用 (APPROVED)
  - 🟡 琥珀 = 待复核 (REVIEW_REQUIRED)  
  - 🔴 红 = 需重跑 / 有问题 (RERUN)
- **高信息密度**：减少留白，数据表格紧凑但层次分明
- 微交互：diff 逐行淡入、柱状图 hover 高亮对应样本

### 页面结构
1. **顶部栏**：版本选择器 A/B、导出按钮、全局状态摘要
2. **左侧导航**：看板 / 分布统计 / 评测回放 / 版本管理 / 反馈日志
3. **主内容区**：按当前选中模块渲染
4. **底部状态栏**：数据一致性哈希、最后同步时间
