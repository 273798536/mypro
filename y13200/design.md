# 巡演耳返版本复核系统 - 设计方案

## 1. 需求分析与核心痛点梳理

### 1.1 业务背景
"巡演耳返版本复核"是现场音频制作流程中的关键环节，涉及厂牌运营录入、现场老师复核决策、音频材料分批提交等多个角色和场景。

### 1.2 核心痛点与对应解决方案

| 痛点描述 | 业务影响 | 设计解决方案 |
|---------|---------|-------------|
| 文件名和曲目表对不上 | 最耽误人的环节，不是录入而是对齐 | 自动文件名解析 + 智能匹配 + 人工校验三重机制 |
| 异常点要能一路点回材料 | 现场老师需要快速定位问题根源 | 全链路追溯设计：图表 → 明细 → 原始材料 → 版本历史 |
| 后补材料不能无声覆盖早先判断 | 音频文件夹常分几次凑齐 | 版本增量合并 + 变更diff + 历史判断保留 + 覆盖提醒 |
| 时码偏半拍宁可挂起也不给假稳定结论 | 避免误导现场决策 | 时码偏差阈值检测 + 自动挂起状态 + 强制人工确认流程 |
| 临时改备注要进历史，不能只改当前页 | 彩排前常有临时调整 | 完整审计日志 + 字段级版本历史 + 变更对比视图 |
| 要看哪些已处理、哪些还要补证据 | 现场老师不看功能表看进度 | 状态驱动的看板视图 + 待办清单 + 证据缺口提醒 |
| 最后输出CSV明细用于沟通 | 功能清单没用，要直接能用 | 预配置CSV模板 + 一键导出 + 沟通场景优化格式 |

### 1.3 核心角色
- **厂牌运营（小孟）**：材料录入、文件名匹配、补充材料
- **现场老师**：复核判断、时码确认、备注修改、最终审批
- **系统管理员**：配置管理、模板维护

### 3.2 数据表设计

#### 3.2.1 曲目表 (tracks)

```typescript
interface Track {
  id: string;
  showId: string;           // 所属场次
  trackNo: number;          // 曲目序号
  title: string;            // 曲目名称
  artist: string;           // 艺人
  expectedDuration: number; // 期望时长(秒)
  expectedTimecode?: string;// 期望时码
  status: TrackStatus;      // 曲目状态
  createdAt: Date;
  updatedAt: Date;
}

type TrackStatus = 
  | 'pending'               // 待录入
  | 'matching'              // 匹配中
  | 'matched'               // 已匹配
  | 'mismatch'              // 不匹配
  | 'reviewing'             // 复核中
  | 'suspended'             // 已挂起（时码偏差等）
  | 'approved'              // 已通过
  | 'rejected';             // 已驳回
```

#### 3.2.2 音频材料表 (audio_materials)

```typescript
interface AudioMaterial {
  id: string;
  trackId: string;          // 关联曲目
  fileId: string;           // 关联文件
  fileName: string;         // 原始文件名
  parsedTrackNo?: number;   // 解析出的曲目号
  parsedTitle?: string;     // 解析出的曲目名
  duration: number;         // 实际时长(秒)
  timecode?: string;        // 检测到的时码
  timecodeDeviation?: number; // 时码偏差(毫秒)
  version: number;          // 材料版本号
  isActive: boolean;        // 是否为当前活跃版本
  submittedBy: string;      // 提交人
  submittedAt: Date;
  sourceBatch: string;      // 来源批次（分批提交标识）
}
```

**关键设计：**
- `version` 字段支持同一曲目多版本材料
- `isActive` 标记当前使用版本，旧版本保留不删除
- `sourceBatch` 记录分批提交的批次信息
- `timecodeDeviation` 记录时码偏差量，用于自动挂起判断

#### 3.2.3 版本历史表 (version_history)

```typescript
interface VersionHistory {
  id: string;
  materialId: string;       // 关联材料
  fieldName: string;        // 变更字段名
  oldValue: any;            // 旧值
  newValue: any;            // 新值
  changedBy: string;        // 变更人
  changedAt: Date;
  changeType: 'create' | 'update' | 'override' | 'note';
  reason?: string;          // 变更原因
}
```

**关键设计：**
- 字段级版本历史，支持备注单独变更追踪
- `changeType: 'override'` 标记后补材料覆盖场景
- `reason` 字段记录变更原因，必填

#### 3.2.4 复核记录表 (review_records)

```typescript
interface ReviewRecord {
  id: string;
  trackId: string;
  reviewerId: string;       // 复核人（现场老师）
  reviewType: 'timecode' | 'quality' | 'note' | 'final';
  decision: 'approve' | 'reject' | 'suspend' | 'pass';
  comment: string;          // 复核意见
  evidenceMissing?: string[]; // 缺少的证据清单
  createdAt: Date;
}
```

#### 3.2.5 审计日志表 (audit_logs)

```typescript
interface AuditLog {
  id: string;
  entityType: 'track' | 'material' | 'review' | 'note';
  entityId: string;
  action: string;
  userId: string;
  timestamp: Date;
```

## 4. 功能模块详细设计

### 4.1 模块一：文件名智能匹配模块

**核心逻辑：**

```
文件名解析流程：
  输入：原始文件名（如 "01_夜曲_周杰伦_立体声_v3.wav"）
  步骤1：正则解析提取字段（曲目号、曲名、艺人、版本）
  步骤2：与曲目表进行多维度匹配（序号、名称相似度、艺人）
  步骤3：计算匹配置信度
  步骤4：置信度 >= 90% 自动匹配，>= 70% 建议匹配，< 70% 人工介入
  步骤5：生成匹配结果，标记异常
```

**匹配规则优先级：**
1. 曲目号精确匹配（最高优先级）
2. 曲名相似度（Jaro-Winkler算法，阈值0.85）
3. 艺人匹配
4. 时长接近度（允许±5秒偏差）

**异常标记：**
- `文件名序号不连续`
- `曲名相似度低`
- `时长偏差超过阈值`
- `找不到匹配曲目`

### 4.2 模块二：版本管理与增量合并

**后补材料处理流程：**

```
新批次材料到达 →
  检查该曲目是否已有材料 →
    无 → 直接创建新版本，标记为active
    有 → 版本号+1，计算与上一版本的diff →
      diff为空 → 提示"内容无变化，无需提交"
      diff存在 → 弹框提示："该曲目已有v1版本，是否覆盖为v2？" →
        用户确认 → 新版本标记为active，旧版本保留为历史，记录override原因
        用户取消 → 保留为非活跃版本，供后续参考
```

**版本对比能力：**
- 文件名对比
- 时长对比
- 时码对比
- 音频波形可视化对比（可选）

### 4.3 模块三：时码检测与自动挂起

**检测逻辑：**

```typescript
function checkTimecodeDeviation(material: AudioMaterial, track: Track): CheckResult {
  const deviation = calculateDeviation(material.timecode, track.expectedTimecode);
  
  if (Math.abs(deviation) <= 100) { // ≤ 100ms，自动通过
    return { status: 'pass', deviation };
  } else if (Math.abs(deviation) <= 500) { // 100~500ms，警告但不挂起
    return { status: 'warning', deviation, message: '时码轻微偏差' };
  } else { // > 500ms（半拍），自动挂起
    return { 
      status: 'suspend', 
      deviation, 
      message: '时码偏差超过半拍，已自动挂起，请现场老师确认'
    };
  }
}
```

**挂起状态特性：**
- 曲目卡片显示醒目的红色"已挂起"标签
- 自动进入"待现场老师确认"清单
- 不允许自动通过，必须人工决策
- 可选择"确认偏差可接受"或"驳回重录"

### 4.4 模块四：全链路追溯

**追溯路径设计：**

```
图表视图（总览Dashboard）
    ↓ 点击异常点
曲目列表（筛选异常状态）
    ↓ 点击具体曲目
曲目详情页
    ├─ 基本信息（曲名、序号、期望时长）
    ├─ 材料信息（当前版本 + 历史版本切换）
    │    ├─ 文件名、时长、时码、偏差值
    │    ├─ [追溯按钮] → 原始文件预览/播放
    │    └─ [版本历史] → 查看所有版本变更
    ├─ 复核记录（时间线）
    │    ├─ 每次复核的时间、人员、结论
    │    └─ 备注变更历史（字段级diff）
    └─ 审计日志（完整操作记录）
```

**追溯入口设计：**
- 所有异常标签均可点击跳转
- 状态标签悬停显示快速预览
- 每页右上角"查看溯源"按钮

### 4.5 模块五：备注历史管理

**备注字段设计：**

```typescript
interface TrackNote {
  id: string;
  trackId: string;
  content: string;          // 备注内容
  createdBy: string;        // 创建人
  createdAt: Date;          // 创建时间
  isActive: boolean;        // 是否当前有效
  previousNoteId?: string;  // 上一条备注ID（形成链表）
}
```

**备注变更流程：**
1. 点击"编辑备注"按钮
2. 弹出编辑器，显示当前备注内容
3. 下方展示历史备注列表（时间倒序）
4. 提交新备注时，旧备注自动标记为非活跃
5. 变更记录写入 `version_history`，`changeType: 'note'`

**备注历史视图：**
- 时间线展示所有备注
- 支持对比任意两条备注的diff
- 显示修改人和修改时间

### 4.8 模块八：CSV导出模块

**预设导出模板（沟通场景优化）：**

#### 5.2.1 异常点高亮与追溯
- 所有异常状态使用醒目的颜色编码：
  - 🔴 红色：已挂起、不匹配
  - 🟡 黄色：警告、待确认
  - 🟢 绿色：已通过、正常
  - ⚪ 灰色：待处理
- 悬停异常标签显示快速预览卡片
- 点击异常标签直接跳转至对应问题详情

#### 5.2.2 版本覆盖确认
后补材料可能覆盖旧版本时，弹出确认框：

```
⚠️ 版本覆盖确认

曲目：03_青花瓷
当前版本：v2（2026-06-14 10:30 提交）
新版本：v3（2026-06-14 15:20 提交）

变更内容：
  • 文件名：青花瓷_现场版.wav → 青花瓷_现场版_v3.wav
  • 时长：245s → 248s
  • 时码：00:03:20.100 → 00:03:20.720（偏差+620ms）

✅ 旧版本会保留在历史记录中，不会删除

请输入覆盖原因（必填）：
[ 后补的最终版本，时码已重新对齐   ]

[ 取消 ]  [ 确认覆盖为最新版本 ]
```

#### 5.2.3 时码挂起确认
现场老师处理挂起项时的交互：

```
⏸️ 时码偏差挂起确认

曲目：01_夜曲
期望时码：00:04:30.000
实际时码：00:04:30.620
偏差量：+620ms（约半拍）

材料历史：
  • v3（当前）：偏差+620ms，2026-06-14 15:20
  • v2：偏差+150ms，2026-06-14 10:30
  • v1：偏差-80ms，2026-06-13 18:00

请选择处理方式：

( ) 确认偏差可接受 → 标记为通过，记录备注
    备注：[ 彩排时现场确认，偏差在可接受范围内  ]

( ) 驳回，要求重录 → 返回运营重新提交

( ) 保留挂起状态 → 延后处理

[ 提交决策 ]
```

## 8. 关键设计决策总结

| 决策点 | 决策内容 | 依据 |
|-------|---------|------|
| 版本管理策略 | 多版本保留，不删除历史 | 后补材料不能覆盖早先判断 |
| 时码偏差处理 | >500ms自动挂起，强制人工确认 | 宁可挂起也不给假稳定结论 |
| 备注变更 | 字段级历史记录，形成变更链 | 改动要进历史，不能只改当前页 |
| 数据追溯 | 全链路可追溯，图表→明细→材料 | 异常点要能一路点回材料 |
| 导出设计 | 多场景CSV模板，非功能清单 | 最后给人看的是能直接沟通的明细 |
| 主视图 | 状态驱动的看板，待办优先 | 现场老师看的是已处理/待处理 |
